# Лимиты и повторные попытки

[← К оглавлению](../../README.md)

## Ограничение частоты запросов

При превышении допустимой частоты запросов API отвечает `429 Too Many Requests` с кодом
`RATE_LIMIT_EXCEEDED` и заголовком `Retry-After` — через сколько **секунд** можно повторить:

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-Correlation-Id: 7f3c2b1e-0000-4000-8000-000000000013

{
  "code": "RATE_LIMIT_EXCEEDED",
  "message": "Too many requests. Retry after the time given in Retry-After.",
  "correlationId": "7f3c2b1e-0000-4000-8000-000000000013"
}
```

Конкретные значения лимитов контрактом не фиксируются. Ориентируйтесь на `429` и `Retry-After`.
Тот же заголовок `Retry-After` приходит с `503 SERVICE_UNAVAILABLE`.

## Какие методы безопасно повторно отправить

| Запрос | Безопасность повтора | Почему |
|---|---|---|
| Любой `GET` | Да | Только чтение |
| `PUT /configuration` | Да | Полная замена: повтор с тем же телом даёт тот же результат |
| `POST /commands` **с** `Idempotency-Key` | Да, с тем же ключом и телом | Сервер вернёт исходный ответ, дубль не создастся |
| `POST /commands` **без** ключа | **Нет**, после таймаута/`5xx` | Команда могла быть принята — повтор создаст вторую |

## При каких кодах ответа допускается повторное отправление запроса

| Ответ | Повторное отправление запроса  | Когда |
|---|---|---|
| `429` | Да | Через `Retry-After` секунд |
| `503` | Да | Через `Retry-After` секунд |
| `502`, `504` | Да | С экспоненциальной паузой |
| `500` | Ограниченно | 1–2 раза с паузой, только для безопасных запросов (таблица выше) |
| `409 DEVICE_BUSY`, `409 IDEMPOTENCY_REQUEST_IN_PROGRESS` | Да | Через паузу |
| `409 DEVICE_NOT_READY` | Да, но осмысленно | После того как устройство перейдёт в нужное состояние (Рекомендуется проверить `/status`) |
| `400`, `403`, `404`, `422`, `409 IDEMPOTENCY_KEY_REUSED` | Нет | Повтор даст тот же результат — исправьте запрос |
| `401` | Один раз | После обновления токена |
| Таймаут сети, нет ответа | Да | Только для безопасных запросов (таблица выше) |

## Рекомендуемая стратегия

- Экспоненциальная пауза с разбросом: `пауза = min(базовая × 2^попытка, максимум) ± случайная доля`,
  например база 1 с, максимум 30 с.
- Если есть `Retry-After` — используйте это значение, а не свой период.
- Ограничьте число попыток (например, 3–5) и общее время.
- Логируйте `X-Correlation-Id` каждой попытки.

```javascript
async function withRetry(fn, { attempts = 4, baseMs = 1000, maxMs = 30000 } = {}) {
  for (let i = 0; ; i++) {
    try {
      return await fn();
    } catch (e) {
      if (!e.retryable || i + 1 >= attempts) throw e;
      const retryAfter = Number(e.retryAfterSeconds);
      const backoff = Math.min(baseMs * 2 ** i, maxMs) * (0.5 + Math.random() / 2);
      await sleep(Number.isFinite(retryAfter) ? retryAfter * 1000 : backoff);
    }
  }
}
```
