# Работа с Postman-коллекцией

[← К оглавлению](../README.md)

## Что входит

| Файл | Что внутри |
|---|---|
| `signal-generator-api.postman_collection.json` | Коллекция «Signal Generator Management API» (формат v2.1): 72 запроса с тестами и сохранёнными примерами ответов |
| `signal-generator.postman_environment.json` | Окружение «Signal Generator — Example» с переменными |

## Импорт

1. В Postman нажмите **Import** и перетащите оба файла.
2. Выберите окружение **Signal Generator — Example**.
3. В окружении заполните `accessToken` (столбец **Current value**) и сохраните (`Ctrl+S`).

## Переменные окружения

| Переменная | По умолч. | Кто задаёт | Назначение |
|---|---|---|---|
| `baseUrl` | `https://api.example.com` | Вы | Адрес API или мок-сервера |
| `useMock` | `false` | Вы | `true` — работа с мок-сервером Postman (см. ниже) |
| `accessToken` | пусто (secret) | Вы | Токен доступа |
| `deviceId` | `sg-001` | Вы | Устройство для всех запросов |
| `commandId` | `cmd-10001` | Тесты | Последняя отправленная команда; подставляется в «Get command execution status» |
| `idempotencyKey` | — | Скрипт | Ключ сценария идемпотентности (шаг 1) |
| `idempotentCommandId`, `idempotentLocation` | — | Тесты | Результат шага 1 для сравнения на шаге 2 |
| `telemetryCursor` | — | Тесты | `nextCursor` со страницы 1 телеметрии |
| `telemetryLastTimestamp` | — | Тесты | Время последней записи страницы 1 |

## Структура коллекции

| Папка | Что внутри | Порядок запуска |
|---|---|---|
| **Devices** | Сведения и статус устройства | Любой |
| **Configuration** | Чтение и замена конфигурации | Любой |
| **Commands** | START, STOP, RESET и статус команды | Сначала команда, потом статус: `commandId` сохраняется автоматически |
| **Idempotency scenarios** | Шаги 1–3: новый ключ, повтор, тот же ключ с другим телом | Строго 1 → 2 → 3 |
| **Telemetry** | Обычный запрос и чтение по страницам | «Page 1» перед «Page 2» |
| **Response codes check** | По каждой операции — все объявленные коды ошибок (58 запросов) | Любой; на реальном API — отдельно (см. ниже) |

## Мок-сервер

Каждый запрос содержит заголовок `x-mock-response-name` с именем сохранённого примера — по нему
мок-сервер Postman решает, какой ответ вернуть. Скрипт коллекции (Pre-request) отправляет 
заголовок **только при `useMock = true`**.

**Работа с мок-сервером**

1. Создайте мок (на коллекции **⋯ → Mock collection**).
2. Удобнее завести отдельное окружение: «Signal Generator — Mock».
3. В нём задайте `baseUrl` = адрес мока и `useMock` = `true`. Сохраните.

**Ограничения мока.** Мок не хранит состояние и всегда отдаёт сохранённый пример. На нём
проверяется только формат ответов: например, шаг 2 сценария идемпотентности «проходит», потому что
мок возвращает тот же пример, а не потому что сервер распознал повтор.

## Что проверяют тесты

**Рабочие запросы** (Devices, Configuration, Commands, Telemetry): код ответа, формат JSON,
заголовок `X-Correlation-Id`, наличие обязательных полей (лишние поля допустимы), допустимые
значения и диапазоны, формат дат RFC 3339. Плюс по смыслу операции: конфигурация в ответе равна
отправленной; `Location` указывает на созданную команду; записи телеметрии отсортированы,
их не больше `limit`; вторая страница идёт после первой.

**Response codes check**: общие проверки записаны один раз в скрипте папки
(**Scripts → Post-response** у папки) и выполняются для каждого запроса — формат JSON,
`X-Correlation-Id`, схема `Error`, совпадение `X-Correlation-Id` и `correlationId`, `Retry-After`
для 429 и 503. В самих запросах — только код ответа и значение `code`; у 401 — ещё
`WWW-Authenticate`.

## Запуск всей коллекции

**В Postman:** на коллекции **⋯ → Run collection**, выберите окружение, нажмите **Run**.

## Частые проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| `500` и тело `{"error": {"name": "serverError", "message": "ESOCKETTIMEDOUT"}}` | Внутренний таймаут облачного мок-сервера Postman, не ошибка API | Повторите запрос; проверьте [status.postman.com](https://status.postman.com); уберите задержку в настройках мока (*Simulate a fixed network delay*); при необходимости пересоздайте мок |
| `mockRequestNotFoundError` | Мок не нашёл пример с таким именем: он привязан к другой копии коллекции | **Mock servers → мок → ⋯ → Edit**: проверьте коллекцию; переимпортируйте с **Replace** |
| Мок возвращает не тот пример (например, ошибку вместо 200) | Заголовок `x-mock-response-name` не отправлен: `useMock` не `true` | Проверьте значение `useMock` (строго `true`), выбранное окружение, сохранение (`Ctrl+S`). Отправленные заголовки видны в **Console** |
| `Could not send request` | В `baseUrl` пример-адрес `https://api.example.com` | Укажите адрес API или мока |
| Все запросы — `401` | Не заполнен или истёк `accessToken` | Заполните **Current value** и сохраните |
| «Get command execution status» — `404` | Команда ещё не отправлялась или не то окружение | Сначала выполните запрос из папки Commands |
| «Page 2» пропущен, в консоли «нет telemetryCursor» | «Page 1» не выполнялась или вернула `nextCursor: null` | Выполните «Page 1»; если записей мало — уменьшите `limit` до 1 |
| Шаг 2 идемпотентности падает на сравнении `commandId` | Шаг 1 не выполнялся или вернул не `202` | Запускайте шаги строго 1 → 2 → 3 |
| В тесте «Тело разбирается как JSON» ошибка | Ответ не JSON — пришёл от прокси или шлюза, а не от API | Посмотрите тело ответа и `X-Correlation-Id` (если есть) |

Отличить ошибку API от ошибки инфраструктуры просто: ошибка этого API всегда содержит `code`,
`message`, `correlationId` и заголовок `X-Correlation-Id`.
